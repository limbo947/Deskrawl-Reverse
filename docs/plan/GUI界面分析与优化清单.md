## 1. UI 视觉层

### V1 【中】输入控件的禁用态与启用态外观完全相同，可交互性不可见 ✅
- **现象**：QSS 只给 `QPushButton:disabled` 定了颜色（`style.qss:79`），`QLineEdit/QSpinBox/QDoubleSpinBox/QComboBox` 没有 `:disabled` 规则（`style.qss:80-87`）。像素取样实测：词条表「类型」列（`item_editor.py:140-152` 主动 `setEnabled(False)` 锁死的下拉）与旁边启用中的「数值」输入框**底色完全相同**（均为 `#262B30`，占比 88%～91%），并且**保留了同样的下拉箭头**——放大 6 倍后两者外观无法区分。
- **影响**：词条表里最像"可点、可改"的那一列恰恰是被锁死的；用户会反复尝试点它。而且「类型」列只有唯一取值「加法」（`_ALLOWED_TYPES = [0]`），用"下拉"这个形状承载单值本身就是误导。
- **建议**：① 把「类型」列从禁用下拉改为**纯文本单元格**（去掉 QComboBox，直接在表格里渲染「加法」二字）——既消除误导，又减少 2×行数×1 个控件；② 若仍需保留控件形态，则补 `:disabled { color:#6B7076; background:#212529; border-color:#282D32; }` 并 `::drop-down` 一并压暗（与 V4 同批）。

### V2 【中】`state` / `trend` 属性选择器只写了一半，错误态被渲染成标题 ✅
- **现象**：`widgets/dps_meter.py:105,107` 设了 `setProperty('state','offline'|'live')`，但 `style.qss` 里**没有任何 `[state=...]` 规则**；`_apply_trend` 的 `[trend]` 有规则（`style.qss:164-165`）但 `state` 没有。截图里「未定位到 DPS 计（需在训练假人地图）」以 `#dpsMeterValue` 的 **18px 半粗大字**呈现。
- **影响**：一句"没读到数据"的失败提示，视觉权重与"当前/候选 DPS"结论数字同级，同屏出现两个大字结论互相抢注意力，用户第一眼会以为那是本页主要结果。`setProperty` 也因此成为死钩子（改了属性毫无视觉反馈）。
- **建议**：二选一——① 补 `QLabel#dpsMeterValue[state="offline"] { color:#9AA0A6; font-size:12px; font-weight:400; }`（并给 `QFrame#dpsMeter[state="offline"]` 弱化描边），让失败态自然降级；② 若不需要差异，删掉两处 `setProperty` 避免误导后人。推荐 ①。

### V3 【低】功能色未收敛到令牌，同一页出现两种"涨绿" ✅
- **现象**：`style.qss` 顶部声明唯一色源（`style.qss:4-19`），但实现里另有 5 个未登记颜色：`#4CAF50`（`style.qss:164` 的 `[trend="up"]`）与 `deltaUp` 的 `#66BB6A`（`style.qss:143`）语义相同却不同值；`#E0E0E0`（`:163`）≠ 正文 `#E8EAED`；`#7F868D`（`:167`）≠ 次要文字 `#9AA0A6`；`#23272C`（`:58,62,106`）未登记为悬停/选中底（声明的 `--bg-hover` 是 `#2E343A`）；`#6B7076`（`:79,119`）未登记为禁用色。
- **影响**：视觉差异细微（两种绿肉眼几乎不可分），但破坏了文件自己声明的"改主题只改这一段"的可维护性契约——按令牌改色会漏掉这 5 处。
- **建议**：把 `#4CAF50` 改为 `#66BB6A`，把 `#E0E0E0/#7F868D` 归到文字令牌，把 `#23272C/#6B7076` 补进色板注释并统一引用。

### V4 【高】复选框指示器实测为纯白方块——全屏最刺眼的主题漏白 ✅
- **现象**：`QCheckBox::indicator` 在 QSS 中**无任何规则**，由平台样式绘制。对「目标状态」区放大 6 倍取证：**未勾选态是一个纯白实心方块（`#FFFFFF`），勾选态是同样的纯白方块 + 深色勾**，共 9 个白色色块铺在 `#1E2226` 深底上。同成因的未样式化子控件还有：`QComboBox::drop-down/::down-arrow`（箭头为平台浅灰）、`QSpinBox` 上下按钮、`QHeaderView` 排序方向指示（截图不可见）、`QMenu::separator`、`QSplitter::handle`（实测不足 3px，抓不住）。
- **影响**：这是本次评估中**最明显、最容易感知的视觉缺陷**——暗色主题被白色方块"扎穿"，第一眼观感像未完成品；排序方向不可见也让"点击表头排序"失去提示。
- **建议**：① 优先补 `QCheckBox::indicator{width:14px;height:14px;border:1px solid #30353B;border-radius:3px;background:#262B30}` / `:checked{border-color:#4FC3F7;background:#2B5F7A;image:url(...)}` / `:disabled{border-color:#30353B}`；② 依次补 `QComboBox::drop-down{border:none;width:20px}` + `::down-arrow`、`QSpinBox::up-button/down-button` + 箭头、`QHeaderView::up-arrow/down-arrow{color:#9AA0A6}`、`QMenu::separator{height:1px;background:#30353B;margin:4px 8px}`、`QSplitter::handle{background:#30353B}` + `setHandleWidth(6)`；③ 交工后实机再截图确认 9 个白块消失。
- **注**：这也解释了为什么 V5（未设 Fusion）值得先做——Fusion 下这些子控件的默认图形本身就是可控的深色系，补规则的工作量会小很多。

### V5 【中】未指定 QStyle，QSS 覆盖率不可控 🔶
- **现象**：`app.py:398-401` 只 `setApplicationName` + `setStyleSheet`，没有 `app.setStyle('Fusion')`。未覆盖的子控件（V4 全部）以及 `QMessageBox` 图标区、`QTextEdit`（导入详情的 DetailedText）、`QSlider` 的 `::sub-page` 等，绘制行为随平台样式（Windows 上是 `QWindows11Style`）变化。
- **影响**：同一份 QSS 在 Windows 主题/Win11 风格更新后可能"换脸"，而仓库没有视觉回归网能发现（见 T7）。
- **建议**：`build_application` 里加 `app.setStyle('Fusion')`，让未覆盖控件也走同一套可控的绘制路径；这一步同时会让 V1/V4 的补丁效果在各机器上一致。⚠️ 需实机复核一次截图（Fusion 的复选框/滚动条与 Win11 风格不同）。

### V6 【低】字号/间距令牌表与实现不一致 ✅
- **现象**：`style.qss:17-19` 声明「间距 4/8/12/16/24、字号 16/13/12、圆角唯一 4px」，实现里存在字号 `22/20/18/11px`、间距 `2px/6px/10px 16px/8px 12px/0 4px`、圆角 `2px/3px/5px/6px`（`:131-136`）。
- **影响**：令牌表是"约定"而非"规格"，改主题时无法机械替换，新人会照着令牌表改而漏掉例外。
- **建议**：把语义大字号（22/20/18/11）与状态圆角（滚动条 5px、滑块 6px）补进令牌注释作为"例外白名单"，明确它们是刻意的。

### V7 【中】属性表两种口径共用同一套表头，同一列名两种语义 ✅
- **现象**：`widgets/stat_table.py:17` 定义 `['属性','基础值','加法','百分比加算','连乘系数','最终值']`；计算口径按 `[name, base, flat, add, mult, final]` 填充（`:42-43`），面板口径按 `[str(stat), flat, cond, pct, mult, text]` 填充（`:49-52`）。于是**面板口径下「加法」列装的是条件层**（值形如 `+0.75`），真正的平坦层被塞进「基础值」列。
- **影响**：同一张表在两种模式下含义不同，只有表格上方那小字 hint（`:55-58`）能说明；用户对照游戏「属性」页时会把条件层误读成加法层，属"看起来合理但读错口径"的隐性误导。
- **建议**：让表头随口径切换——`set_panel_view` 时 `setHorizontalHeaderLabels(['属性','平坦层','条件层','百分比加算','乘区','面板显示'])`，`set_sheet` 时恢复计算口径表头；并给「条件层」列加 `+` 号颜色（可复用 `deltaUp/deltaDown` 令牌）。

### V8 【低】跨列对齐基线断裂（已用像素扫描证实）✅
- **现象**：① 候选卡片比当前卡片多一条表单项（`item_editor.py:202-208` 的「强化/宝石」勾选行）＋一条更长的会换行元信息（`:271-284`），使两侧词条表**垂直错开约一行**——像素扫描佐证：同一条水平线 y=489 上，左侧表格落在网格线色 `#30353B`（302px 连续段），右侧表格落在行内容色 `#262B30`（293px 连续段），说明两表差了一行高度；② 锁定态把「×」列整体隐藏（`item_editor.py:94`）后留下一个空列，右侧留白；③ 对比结果三格大数字按等宽 QGridLayout 排（`compare_view.py:22-37`），与下方技能表的列宽无关，两组数字不共享纵向对齐线。
- **影响**：观感"手工拼装"而非"设计过"，也削弱了逐行比对（同一行的当前/候选值不在同一水平线上）。
- **建议**：① 给 `ItemEditor` 加一行固定的空位（或在当前侧也渲染同高的只读占位），使两侧表头严格对齐；元信息标签限高单行 + 省略号 + tooltip 承载全文；② 锁定态保留列宽或整列 `setColumnWidth(0)`；③ 大数字改用与技能表同源的列宽比例（`setColumnStretch` 对齐到 技能/当前/候选 三列）。

### V9 【中】无响应式降级，最小窗口下三栏挤压 ✅
- **现象**：侧栏 `setFixedWidth(188)`（`navigation.py:25`）、右栏 `setMinimumWidth(300/330)`（`compare_page.py:40`、`role_page.py:33`）、splitter 初值绝对值（`compare_page.py:44`、`role_page.py:38`、`assembly_center.py:173`）、窗口最小 960×640（`app.py:102`）。截图所用窗口宽度下，装备对比页已是"左侧双编辑器 + 右栏表单"三列并排，词条表内出现挤压。
- **影响**：① Windows 缩放会让"可用逻辑宽度"缩水——1920×1080 物理屏在 150% 缩放下只剩 1280×720 逻辑点，此时窗口最小宽 960 逻辑点意味着只剩 320 点余量，三栏挤压会远早于 100% 缩放时发生；② 无法把侧栏收起换宽度，也无法把双栏堆叠。
- **建议**：① 侧栏改为可折叠（`QToolButton` 切换 `setVisible`），或宽 160↔188 自适应；② `QSplitter` 的 childrenCollapsible 与 `setStretchFactor` 明确，允许把右栏拖到最小后自动折行（`QVBoxLayout` 在 <1100px 时把双栏转为上下堆叠，用 `resizeEvent` 切换）；③ 把绝对像素初值改成按窗口宽度的比例（`setSizes` 用 62%/38% 之类的相对值）。

### V10 【低】无图标/品牌位，188px 侧栏全空 ✅
- **现象**：`resources/` 只有 `style.qss`，无图标资源；全仓无 `QIcon`/`setWindowIcon`；侧栏 3 个条目下留出约 80% 的空白（`navigation.py:11-26`，docstring 写着"图标留白"但图标并未实现——注释与实现漂移）。
- **影响**：任务栏显示 Qt/Python 默认图标；侧栏大面积留白浪费了最稳定的视觉区域（可承载版本/数据源徽标）。
- **建议**：① 加一枚 64×64 的窗口/任务栏图标（可用现有 SVG 或生成一张，放 `resources/`）；② 侧栏底部加"数据源徽标"（见 U4），把留白变成状态位；③ 修掉 `navigation.py` docstring 里"图标留白"的表述。

### V11 【中】页面副标题超长，信息层级塌缩成两级标题 + 大段说明 ✅
- **现象**：`compare_page.py:49` 的副标题 130+ 字（"编辑当前/候选装备（当前件来自导入时固定只读）…请逐槽评估）"），12px 弱化色单行铺满整个内容区宽度（截图可见）。性能提示、口径边界、操作提示三类信息混在同一句里。`common.py:63-76` 的 `page_header` 只有标题/副标题两级。
- **影响**：① 用户扫不到"这页要干什么"的一句话结论；② 长句里的关键约束（"一次只对比一个槽位"、"当前件只读"）被淹没；③ 页面顶部被说明文字占据，挤占结果区高度。
- **建议**：① 副标题压到一句 ≤30 字，其余拆为"①就地提示（tooltip/ⓘ按钮）②页面内可折叠的「口径说明」抽屉"；② 给 `page_header` 加第三级"ⓘ 帮助"入口（`QLabel` + `setToolTip` 或点击弹层），把 V11/U1 的长文集中到一处。

### V12 【中】Windows 标题栏未暗色化，窗口顶端 30px 是纯白 ✅
- **现象**：截图垂直扫描（x=960）：y=1～30 为纯白 `#FFFFFF`，y=31 起才是应用的 `#1A1D20` 菜单栏。即窗口顶部有一条 30px 的**系统标题栏**，在暗色应用之上形成一条亮色横带；全仓无 DWM 暗色标题栏调用。
- **影响**：暗色应用被白色边框"框住"，观感割裂（截图里这是除 V4 白块外第二显眼的亮色区域）；在亮色桌面环境下尤其突兀。
- **建议**：Windows 上调用 `DwmSetWindowAttribute(hwnd, DWMWA_USE_IMMERSIVE_DARK_MODE(20), 1)`（Win10 1809+ 为 19/20，Win11 为 20，需 try/except 兜底——非 Windows 平台静默跳过）。实现位置放在 `run_gui`（`app.py:404-408`）建窗之后、`show()` 之前；为避免引入新依赖，可用 `ctypes` 直接调 `dwmapi`。⚠️ 需实机复核（部分 Win10 版本不生效，属"尽力而为"）。

### V13 【低】多层边框嵌套，同屏 5 层矩形造成视觉噪音 ✅
- **现象**：以装备对比页为例，从外到内叠加：页面边距 → 卡片 `QGroupBox` 描边（`style.qss:29-35`）→ 词条表 `QTableView` 边框（`:104-111`）→ 单元格网格线 `gridline-color`（`:107`）→ 单元格内控件自身边框（`:80-86`）。放大 6 倍可见每行词条被"表格框 + 网格线 + 输入框框"三层线切分，一屏内矩形框数量极多。
- **影响**：视觉噪音掩盖了真正需要突出的信息（Δ 结论）；也让"分组"这一语义靠边框而非留白表达，密度感偏重。
- **建议**：① 在 `QGroupBox` 内部的表格上去掉自身外框（`QTableView { border: none }` 或对内部表设 `setFrameShape(NoFrame)`）；② 表格只保留水平方向分隔（`setShowGrid(False)` + 行交替底色），去掉竖网格线；③ 卡片标题栏与内容之间用 8px 留白替代内层描边。

## 2. 交互功能层

### I1 【中】每次编辑都全量刷新，并把状态栏永久改成"已刷新" ✅
- **现象**：任何编辑 → `changed` → `profileChanged` → `_refresh_all`（`app.py:142-145, 382-387`），末尾 `showMessage(f'构建「{name}」已刷新')` **不带超时**（`app.py:387`，Qt 语义 = 永久停留）。
- **影响**：① 敲一个字、拖一次滑条，状态栏就永久变成"已刷新"，并覆盖掉导入摘要（`app.py:300`）、会话恢复说明（`:183-185`）、指纹告警（`:255`）等真正有价值的一次性消息——**信息不可逆丢失**；② 同屏每字符重算一次（实测 6-10 ms，不至于卡，但纯属无谓）。
- **建议**：① `showMessage(..., 2000)` 加超时；② 更彻底：编辑类刷新不发状态栏消息（刷新是持续状态，不是事件），只保留导入/保存/加载/恢复这类一次性消息；③ 名称框等自由文本输入加 150-250 ms 防抖（见 I2）。

### I2 【低-中】自由文本输入无防抖 🔶
- **现象**：`item_editor.py:196` 的 `name_edit.textChanged` 逐字符写回草稿并触发全量刷新；装备名对计算无影响（只影响特效反查），却每次都重算技能秒伤表。
- **影响**：无谓重算 + 放大 I1 的状态栏抖动；长名称输入时每秒十余次重算。
- **建议**：名称输入改为 `editingFinished` + 250 ms `QTimer` 合并触发；数值类 `valueChanged` 保持即时（符合"拖滑条看 Δ 实时变"的预期）。

### I3 【中】静默改写持久化模型：切槽会自动往候选草稿里填数据 ✅
- **现象**：`equipment_editor.py:107-109` 在候选为空且当前件非空时，把当前件**深拷贝**进 `slot_candidate`；`_drafts`（`:100-101`）对任意访问过的槽 `setdefault` 建草稿。这些草稿随会话状态（`app.py:187-196`）与构建存档（`profile.py:322-323`）落盘。
- **影响**：用户"只是切到戒指槽看了一眼"，模型里就多出一份候选拷贝并写入磁盘；之后会话恢复会带着这些幻影候选回来。属于"看=写"的隐性副作用，也解释了为何未对比的槽会显示 Δ=0.00%。
- **建议**：① 切槽只渲染、不写入：候选为空时显示"空候选（Δ=0 基线）"提示 + 一个显式按钮「以当前件为起点」（点一下才拷贝）；② 或保留自动预填但加一次性提示条（"已用当前件预填候选，可直接改"）+ 在 `profile.to_dict` 里剔除"未改动"的空草稿。

### I4 【高】装备名解析失败 → 传奇特效静默丢失，界面无任何提示 ✅
- **现象**：`core/localization.py:77-93` 的 `item_internal_name` 查不到时**原样返回**（回落而非报错），`calc_service._effect_mods/_effect_dicts`（`core/calc_service.py:96-111`）随之取不到 `EquipmentEffects`。`--selftest` 的 F3 断言已实证："名字不可解析时 Δ%=-25.793（特效被丢掉）"。而界面侧的告警通道只覆盖 `_negate` 的连乘词条（`calc_service.py:174-188`），名称侧无告警。

### I5 【中】隐式耦合未就地说明，tooltip 覆盖极薄 ✅

## 4. 技术实现层

### T1 【中】`core/memory_import.py` 749 有效行，超过 700 拆分行阈值 ✅
- **现象**：实测有效行 749 / 总行 810（仓库硬上限 800、用户约定 >700 应拆）。`selftest_fixture.py` 681 亦接近阈值。
- **影响**：触及棘轮规则的"必须拆分"线；继续加功能只能靠同步删减，改动成本上升。
- **建议**：把"快照 → CharacterProfile 映射"（α/β 分支、槽位/背包/符文解构）拆到 `core/snapshot_mapper.py`，`memory_import.py` 只留定位链 + 校验（这两块是"只读硬约束"的高压区，值得独占文件）。拆分后按约定在被拆文件 docstring 写明理由，并跑 `--selftest`（`selftest_fixture` 的 β/α 夹具断言会给这次搬迁兜底）。

### T2 【中】DPS 计 1s 轮询常开，永不停止 ✅
- **现象**：`widgets/dps_meter.py:62-66` 在 `GameDpsMeter.__init__` 里 `self._timer.start()`；全仓无 `timer.stop()`（`grep` 实测），也不判页面可见性/游戏是否在跑。而 `core/dps_meter.py:111-140` 的单次读取要做：进程枚举 + 用法槽 256 扫描 + 静态字段解析 + 委托数组扫描（最多 32 个委托）。
- **影响**：① 用户停留在角色页/装配中心、甚至游戏没开时，每秒仍在做一次内存扫描（无谓开销，也是"工具在后台一直摸游戏进程"的观感问题）；② 无法关闭（用户无法自己决定"我不需要实测值"）。
- **建议**：① `app.py` 在页面切换时启停（进对比页 `start`、离开 `stop`），已足够；② 再进一步：窗口 `hide`/最小化时暂停（`QEvent.WindowStateChange` + `isVisible`）；③ 给实测框加一个"实时刷新"开关（默认开），关掉后变手动刷新按钮；④ 失败态（游戏未运行）时把间隔降级到 5 s，避免持续无效扫描。

### T3 【中】QSS 是唯一视觉事实源，但无"选择器 ↔ 代码"对账机制 ✅
- **现象**：`style.qss` 用 `#objectName` 与 `[prop=...]` 两类选择器锚定代码；代码侧对应 `setObjectName`（如 `'modeBanner'/'emptyState'/'deltaUp'`）与 `setProperty`（`trend/state`）。已出现两类漂移：`state` 属性**无规则**（V2，死钩子）、`compare_view.py:42` 用 `objectName='modeBanner'` 表达"对比口径告警"（名实不符）。
- **影响**：改 QSS / 改 objectName 都没有回归网保护，视觉问题会在重构中静默出现（且 `--selftest` 全部是数值断言，抓不到）。
- **建议**：加一条轻量视觉自检（挂在 `--smoke` 里，零依赖）：① 扫描 `style.qss` 的所有 `#id` 与 `[prop]` 选择器；② 扫描 GUI 源码里 `setObjectName('...')`、`setProperty('trend'|'state'|...)` 的字面量与代码实际引用；③ 断言双向——"选择器都有代码来源"且"属性都有对应规则（或列入显式豁免表）"。这条断言一旦落地，V1–V4 类问题以后无法再偷偷出现，且天然满足"改错必须报红"的仓库原则。
- **注**：本条的豁免表要显式登记 `objectName='modeBanner'` 的二次使用（否则会误报），并在注释里写明理由。

### T4 【低-中】计算链两侧对称分支重复展开 ✅
- **现象**：`core/calc_service.py:238-310` 的 `compare()` 在 `slot==0` 与 `slot!=0` 两条分支里各写一遍"取公共特效 → 求条件暴击 → 求条件伤害 → 应用属性换算"（约 30 行对称代码）；`_equipped_effects` 在每次 `_dps_with`（`:354-373`）里被重解，`rank_candidates`（`:388-400`）因此对每个候选重建整张 `StatSheet` 并重解特效（实测 199 条符文 41 ms，可接受，但随已装备件数线性增长）。
- **影响**：对称逻辑两处维护（改口径容易只改一侧，本仓历史上已发生过宝石分组不对称类 bug）；排序耗时是可接受的但无缓存。

### T5 【低】编辑器"重建"而非"复用"，依赖 `deleteLater` 回收 ✅
- **现象**：`_build_editors`（`equipment_editor.py:104-122`）每次切槽/回填都新建两侧 `ItemEditor`（各含一张 7 行 × 67 项下拉的词条表）并用 `_replace`（`:141-147`）`deleteLater` 旧件。实测离屏基准（无事件循环）widget 计数从 480 涨到 1172，说明回收依赖事件循环。
- **影响**：正常 GUI 有事件循环、不会持续增长，但切槽有 12 ms 重建成本 + 一次全量控件构造/析构；也解释了 `--smoke` 计数与运行时计数差异，给未来的自动化断言埋坑。
- **建议**：① 改成复用：`ItemEditor.set_draft(draft)` 已存在（`item_editor.py:237-239`），切槽时只换草稿与标题（`weapon` 变体差异用两个预建卡片 + `QStackedWidget` 切换）；② 若保留重建，则显式 `old.setParent(None)` 或 `deleteLater` + `QApplication.sendPostedEvents(None, QEvent.DeferredDelete)`，让计数稳定。

### T6 【低】词条单元格用 cellWidget 承载 QComboBox，控件数偏多 🔶
- **现象**：每行 3 个 cellWidget（属性下拉 67 项 + 类型下拉 + 数值 spin）＋ ×，最多 7 行 × 两侧 = 约 42 个控件、其中下拉实例 14 个（每个都复制 67 项 item）。

- **建议**：改用 `QStyledItemDelegate` + 共享 `QStandardItemModel`（属性项构建一次），或在"属性"列用可编辑文本 + 补全（`QCompleter`）。属重构级改动，非必需。

### T7 【中】无 lint/构建配置，视觉与交互回归仅靠 smoke 计数 ✅
- **现象**：仓库"无 lint/构建配置，纯 Python 仓库"；自动测试只有 `--selftest`（56 项，全部为数值/服务层断言）与 `--smoke`（480 widget 计数 + 若干行为断言：词条下拉项数、面板改动→属性表刷新、装配中心搜索/加入/删除、排序、双击、菜单一致性、会话持久化）。
- **影响**：任何 QSS/布局改动都没有断言保护，视觉回归靠人眼；新增控件也不会被计数类断言拦住。
- **建议**：① 落 T3 的选择器对账断言；② 在 `--smoke` 补"关键面板锚点"断言（例如：对比页存在 `dpsBig`×2、`deltaUp|deltaDown`、`modeBanner` 可隐可显；侧栏 3 项；目标状态 9 个勾选；装配中心 5 列）——不追求视觉像素，只固化结构契约；③ 可选引入 `ruff`（`requirements-dev.txt`）做静态检查，但需先确认与"无构建配置"的仓库约定不冲突。

### T8 【低】命名与死代码 ✅
- **现象**：① `widgets/dps_meter.py:40` `self.setTitle = QLabel(...)`——`QFrame` 无 `setTitle`，这里把属性命名为 `setTitle` 并持有一个 QLabel，形似方法覆盖，后续任何 `self.setTitle('x')` 都会崩（正确命名 `self.title_label`）；② `app.py:212-226` 保留 4 个"旧布局别名" property，仅供 selftest/脚本使用；③ `compare_page.refresh` 里 `_sync_meter` 被调用两次（`:71-72`，第二次是"期望未变时也重绘一次"的兜底，代价可忽略但语义重复）；④ `compare_view.py:42` 的 `objectName='modeBanner'` 名实不符（见 T3）。
- **建议**：① 改名为 `title_label`（`App` 内无其它引用）；② 保留别名但加注释注明"仅对 selftest 暴露，勿在新代码使用"（若 selftest 改为经页面属性访问则删除）；③ 无功能影响项可随批次 C 一并清理。

## 7. 不应改动的边界（本清单的红线）

- **只读硬约束**：内存导入链（`memory_reader.py → memory_import.py → memory_snapshot.py`）任何时候不得引入写操作；本清单所有改动都不触碰该链路。
- **selftest 锚点冻结**：`selftest.py` 的 `ANCHORS`（197.9 / 226.3 / +14.32%）与 `_METER_ANCHOR` 随内核一起冻结；改公式或计算口径必须同步锚点，不属于"界面优化"范畴。
- **α 横幅文案锚点**：`common.ALPHA_BANNER_TEXT` 含「降级」关键词，selftest 依赖它；改文案前先确认断言。
- **"当前件只读"设计**：这是对比有效性的前提（`item_editor.set_locked`），优化方向只能是"把只读讲清楚/给出退出口"，不是放开编辑。
- **GUI 不得 import `tools/scripts`**：任何新增的术语表/帮助内容都必须自包含（纯 stdlib + PySide6）。
- **文件行数棘轮**：新增逻辑优先放新文件；`memory_import.py` 只降不升。

### 本轮附带发现并修复的两个真实缺陷（原清单未列）

1. **`--smoke` 会弹模态确认框并在非交互环境挂死**：`_gui_behavior_checks` 步骤 5 的收尾删除调用的是**真** `confirm_delete`（局部补丁在步骤 3 的 `finally` 里已还原）→ 每次跑 smoke 都会在桌面上弹出对话框、进程挂住等点击（这正是本轮 smoke 一度「跑几分钟不结束」的原因）。已把补丁提到函数级（全程短路为「确认」），smoke 从「挂死」变成 **3.6 s**。
2. **`state` 属性挂错控件**：`setProperty('state', ...)` 设在 `QFrame#dpsMeter` 上，而 QSS 规则是写给 `#dpsMeterValue` 的 → 失败态一直按 18px 半粗大字渲染。改为同时挂「卡片 + 结论标签」后，失败态才真正降级为 12px 弱化小字。
