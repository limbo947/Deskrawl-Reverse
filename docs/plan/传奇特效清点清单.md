## 1. 判定口径

| 判定 | 含义 | 能否进「当前↔候选」静态 DPS |
|---|---|---|
| **A** | 数据齐备、可复用现有池/乘区直接建模 | ✅ 能（对比 Δ 直接受益） |
| **B** | 数据齐备，但需新增乘区，或改命中模型/`_rates` | ✅ 能（需扩模型） |
| **C** | 数值型，但取值依赖**运行时状态**（叠层/召唤数/法力比/计数） | ⚠️ 需实机/存档喂值或稳态近似 |
| **D** | 触发/行为类（条件触发的行为），不落在静态 DPS 口径 | ❌ 不建模（写明理由） |

> `D` 类并非「无法折算」：部分带 `Chance` + `List<AbilityEffect>` 的（如 `TriggerEffectsOnHit`）
> 理论上可折「触发率 × 期望伤」，但会把工具从「面板口径」推向「实战模拟」，**当前口径不做**。

## 3. 建议排期

1. **首批（A，32 条）**：可复用现有池——`ConditionalDamage`/`ConditionalCritDamage`/`ConditionalCritChance`
   → 条件池与暴击乘区；`AbilityTagCritDamage` → 按技能行过滤；`AbilityModifier`/`AbilityChannelModifier`
   → `ability_mods` 通路；`StatConversion` → `StatSheet` 换算。**对 DPS 数值影响最直接。**
   **进度（2026-10-17）**：**首批 A 全部完成**——组1/组2/组3/组4（含 `StatConversion`），见 §5。
2. **次批（B，22 条）·口径已定案（2026-10-19，用户裁决）**：**不引入「命中数」维度**，维持
   「单目标稳态 · 面板口径」。理由（数据域实测）：`AbilityProjectileCount` 5 条只给
   `ExtraProjectiles` + 10–15° 夹角（扇形散射，单目标命中数取决于目标体积/距离）；
   `LegendaryHelm3` 同一件上 +2 投射物还配存活 −20% / 尺寸 −25%（「多而小近」的平衡设计）；
   `AbilityStrikeSplash` 只有 `Radius`、`AbilitySpawnCount` 只有 `ExtraSpawns`、
   `AbilityProjectileDeflect` 只有 `Deflects/Targeting`——收益全依赖敌群密度与召唤链（后者属 D 面）；
   `AbilityEffectOverride` 10 条的 `OverrideEffects` 只有 `__managed_ref_hash__`（替换段未解出，
   需补解码器，是数据工程而非口径）。**处置**：这 17 条标不建模，UI 在传奇词条行尾标
   「（未计入 DPS）」；`DivineHelmet3` 已接线；`AlwaysHealthConditionalDamage` 待 REA。
3. **C（22 条）·口径已定案（2026-10-19）：不建模**。原以为 `StatPerStatusStack`/`DamagePerStatusStack`
   能直连叠层读取链，实测**前提不成立**：两条特效的状态都是**自身增益**——
   `LegendaryGloves4`/`MonkSetRune1_Effect2` 的 `MonkBasicAttack2Status`（Stackable、MaxStacks 20、
   Duration 4s）与 `LegendaryGloves8Status`（5s），城镇里恒 0 层，战斗中每秒在变，静态导入不可得；
   其余 C 面同理（`AbilityTagApplyStatus` 13 条是「命中施状态」触发链，折算即实战模拟；
   召唤数、法力比、连击计数全是运行时量）。**处置**：不建模，UI 的同一条「（未计入 DPS）」已覆盖；
   若要模拟层数，须新增「假定层数」手填输入（未做，属实战模拟口径）。
4. **D（35 条）**：**不建模**——触发/行为类不落在「面板 ↔ 候选 Δ」口径；若将来要，需先立「实战模拟」口径。

## 7. 解码修复与天赋取值公式（2026-10-20）

### 7.1 `decode.py` 缺「内联 class 前 4 字节对齐」

`TalentEffect_*` 里 `RequireOnSelf`（bool，1 字节）后面紧跟 `LeveledFloat`（嵌套 class）时，
`decode_value` 直接进 `decode_struct` 而没有重对齐 → 整个结构错位 3 字节，`ObscuredFloat`
解出 `1e-39` 反常量、`__tail__` 非零（这个非零 tail 就是错位的指纹）。

修复：`decode_value` 的 class 分支前补 `r.align(4)`。影响面（逐条实测）：**TalentEffects 35 条**
（9 类：`ConditionalBonusDamage` 7、`AbilityApplyStatus` 11、`AbilityKnockback` 3、
`TriggerAbilityCooldownReduction` 2、`AbilityTriggerAbility` 3、`NthAbilityApplyStatus` 2、
`HitsTakenTriggerEffect` 4、`CheatDeath` 1、`CastSequenceDamage` 2）；
**EquipmentEffects 与 LifeSkillEffects 零影响**。只重导 `TalentEffects.json`
（`tools/scripts/dump_talent_effects.py`），避开 `dump_all2.py` 的 assets_cache 缩水风险。

### 7.2 `LeveledFloat` 的取值公式与步长

- **公式**：`Base + (等级-1) × PerLevel`（`LeveledFloat` 语义，与 `engine.leveled_value` 一致），
  **不是**「每级累加求和」——两者只在 base==per 时碰巧相等（死神之刃 10/10 时都是 1.0）。
- **步长**：`PerLevel` 在 `Base + 0x14`（`ObscuredFloat` 实际 0x14 字节）。配置里原来的 `0x10`
  读到的是噪声；此前「per 恰好很小」让错误公式也能给出对的值，两个错误互相抵消。
- 实机复核（2026-10-20）:死神之刃 ChannelSpeed = **1.0**（+100%，与 tooltip 一致）、
  强攻伤害 = **1.5**（0.15 + 9×0.15）、嗜血 = **0.5**。
