## 1. 背景

GUI v1 选择「手动录入面板」的直接原因：联机模式角色数据不在本地存档（[桌面GUI开发计划.md](桌面GUI开发计划.md) §2、README §5）。本次调研回答：**能否在不修改任何原始数据的前提下，通过内存导入让 GUI 拿到联机角色的真实面板/装备/词条/天赋/巅峰数据**，替代手工录入。

## 2. 数据存在性分析

### 2.1 联机数据流（证据链）

```
登录: Steam ticket (GetTicketForWebApiResponse_t) ──► auth-worker-prod.deskrawl.com
        │  (CloudClient : MonoBehaviour, 静态单例, dump.cs L375582-375653)
        ▼
角色数据下载: 云端 JSON ──► SaveSystem.eea(string) : SaveContainer   ← 解析进内存
        ▼
游玩中: 完整数据活在【运行时对象】里（Player/Inventory/Storage，路径 B）
        SaveSystem.nfn 仅持槽位摘要（OnlineSlots[i].Data = null，spike 实测）

autosave: 运行时状态 ──► 临时装配完整 SaveData（eeu/eeb）──► JsonUtility 序列化
```

## 3. 内存数据结构（全部实测验证）

### 3.1 定位链（路径 B，spike 实测通过）

```
GameAssembly.dll base（本次 0x7FFE51E00000，ASLR 每次启动变化）
  └─ 静态 getter 锚点（扫描方法内 rip 相对加载 → IL2CPP 元数据用法槽）
       GameManager.diw()   RVA 0x75B860 (dump.cs L387132)
       Inventory.eyy()     RVA 0x4EFDA0 (L394090)
       Storage.fmq()       RVA 0x51CA20 (L395779)
       └─ 槽值 = Il2CppClass*（name char* 字段 @+0x10 自校验类名）
            └─ static_fields @ klass+0xB8（实测指令 mov rax,[rax+0xB8] 证实）
                 └─ 单例实例 @ static_fields+0x0（klass 指针回指自校验）
GameManager +0x40 → PlayerCombatController +0x20 → Player 实例
```

辅助链（已被 spike 顺带证实）：`SaveSystem.eea/eed/edy/eeu`（0x7A3EE0/0x7A4360/0x7A3AC0/0x7A5C60）→ `nfi`（static_fields+0x0）→ `nfn @ +0x28`；`edy` 反汇编直接印证 `nfn@0x28`、`OnlineSlots@0x20`、`LocalSlots@0x18` 偏移。

### 3.2 关键运行时字段（dump.cs 实偏移）

| 对象 | 字段 | 偏移 | 类型 |
|---|---|---|---|
| `Character` | `_level` | 0x20 | ObscuredInt |
| | `BaseMaxHealth` / `BaseDamage` | 0x30 / 0x50 | ObscuredLong |
| | `BaseCritChance` / `BaseAttackSpeed` / `BaseDodgeChance` | 0x84 / 0xAC / 0xC0 | ObscuredFloat |
| | `BaseMaxMana` | 0xD8 | ObscuredLong |
| `Player` | `CurrentXP` | 0x180 | ObscuredLong |
| | `BasePrimaryStat` / `BaseLifeOnHit` / `BaseLifeOnKill` | 0x1A0 / 0x1B4 / 0x1C8 | ObscuredFloat |
| | 三层聚合字典 ×5（`nsq/nsr/nsu/nsv/ntc/ntd/nte` 等） | 0x218–0x288 | `Dictionary<StatType, ObscuredDouble>` |
| | 天赋/技能/特效容器 | 0x248–0x348 | `Dictionary<TalentData,int>`、`List<EquipmentEffectBehavior>` 等 |
| `Inventory`（单例） | `nso`（背包 `InventorySlot[]`） | +0x38 | 数组：+0x18 长度，+0x20 元素区 |
| `Storage`（单例） | `nyk`（仓库 `InventorySlot[]`，容量 250） | +0x30 | 同上 |
| `InventorySlot` | `Item(ItemData*)` / `Count` / `ItemUid` / `Locked` | 0x10 / 0x18 / 0x20 / 0x28 | — |
| `ItemData`（SO） | 名字：托管侧 m_Name 为空（Unity 对象名在原生层），**用 `ItemUid` 反查 `data/so_dump/ItemData.json` 与存档注册表** | — | — |

IL2CPP 基元：String（len@0x10, UTF-16@0x14）、Array（len@0x18, data@0x20）、List（_items@0x10, _size@0x18）。类对象 `name` 是 `char*` 指针字段 @+0x10（**需解引用**，v1.0 曾踩坑）。

### 3.3 ACTk `Obscured*` 解码（★ 反汇编实证，非猜测）

布局（dump.cs L657166–657470）：`hash` / `hiddenValue` / `currentCryptoKey` / `fakeValue`（Int/Float 16B+4，Long/Double 32B）。

| 类型 | 读取算法（实证函数） | 加密（逆运算） |
|---|---|---|
| ObscuredInt | `(hidden − key) ^ key`（`kah()` @0x4558A0 中段） | `key + (value ^ key)`（`jzy` @0x455700） |
| ObscuredLong | `(hidden − key) ^ key`（`kas` @0x452340） | `key + (value ^ key)`（`kar` @0x452330） |
| ObscuredFloat | `bswap12(hidden) ^ key`（`jyi` @0x454810；字节 1↔2 互换后异或） | `bswap12(bits ^ key)`（`jyh` @0x4547E0） |
| ObscuredDouble | 字节置换后 `^key`（`jxh` @0x453B70：swap(b0,b1) + 三循环 b4→b5→b7→b4，再异或 key）——**40B 布局**（含 oldByte8 尾字段，L657178），与 Int/Long 的加法式不同 | `permute(bits ^ key)`（`jxg` @0x453B30） |

- 密钥（`currentCryptoKey`）**随机且存在每个结构体内**，无需全局密钥。
- `hash` 字段为 FNV-1a 校验（偏移基 0x811C9DC6，kah() 实证）——只做反篡改检测，读取时可忽略。
- ACTk 检测器（`AntiCheatManager`：SpeedHackDetector + ObscuredCheatingDetector）均为进程内被动检测，只感知**写**，对只读透明。

## 4. 技术实现路径（只读、零注入）

1. **打开进程**：`OpenProcess(0x0410)`（已实测畅通）；
2. **定位基址**：枚举模块取 `GameAssembly.dll` 基址；
3. **定位单例**：扫静态 getter 前缀指令的 rip 相对目标 → 元数据用法槽 → `Il2CppClass`（类名自校验）→ `static_fields@+0xB8` → 实例（klass 回指自校验）。全部偏移集中存 `memory_offsets.json` + GameAssembly SHA-256 指纹，不匹配即提示重新导出 schema；
4. **读取与解码**：沿 §3.2 指针链读取，ACTk 按 §3.3 解码；单遍快照 + 结构校验（Level∈[1,70]、字典键合法、UID 唯一）+ 失败重试；
5. **GUI 对接**：新增 `tools/deskrawl_gui/core/memory_import.py`（仅 ctypes，零新依赖），快照转 `CharacterProfile`；P1 需补充：装备槽运行时容器定位（当前 spike 已确认背包/仓库，装备槽与聚合字典为 P1 内容）。

> 备注：v1.0 曾推荐路径 A（`nfn` 直读），spike 证伪后废弃；路径 A 的定位技术（元数据槽 + static_fields）完整复用于路径 B，无沉没成本。

## 5. 数据一致性影响评估

### 5.1 对游戏：零影响的前提（硬约束，写入设计规范）

1. 仅 `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ)` + `ReadProcessMemory`；
2. **禁止** `WriteProcessMemory` / `CreateRemoteThread` / DLL 注入 / `SuspendThread`（本项目用途完全不需要）；
3. 不改动游戏目录任何文件；不对服务器发送任何构造请求；
4. 读取节流（≥1s 间隔，建议手动触发或 ≤0.5Hz 轮询）。

满足以上四条时，读取在进程外发生，游戏进程无感知，不存在"导入污染原始数据"的通道。

### 5.2 对读取自身：撕裂读（一致性主要风险）

游玩中运行时对象在主线程持续变更，跨多次内存读可能读到中间态。缓解：

- **校验失败即弃**：结构校验 + ACTk 值合理性检查（如暴击率 ∈ [0,1]、血量 > 0）过滤中间态；
- **择时读取**：在城镇/打开背包界面触发导入；
- **单遍快照**：整棵一次拉完后再解析。

### 5.3 新鲜度：客户端快照 ≠ 服务器权威

运行时对象是客户端本地的实时状态；服务器在 autosave 时校验版本（409 冲突）。换装/升级后内存立即反映（比路径 A 的"保存时装配"更新鲜）。UI 须展示快照时间戳并留"重新快照"操作。

### 5.4 反作弊检测器行为（为什么读不会触发）

`AntiCheatManager`（dump.cs L384182-384190）仅有 `SpeedHackDetector`（检测时钟加速）与 `ObscuredCheatingDetector`（检测 Obscured 值被**改写**时 hidden/fake 不一致）。二者均为进程内被动检测，不存在"检测到有人打开了只读句柄"的机制；系统层面亦无 EAC/BattlEye（安装目录与 107 模块枚举确认）。

## 6. 风险评估矩阵（v1.1 更新）

| 风险 | 等级 | 说明 / 缓解 |
|---|---|---|
| 游戏更新导致偏移失效 | **中高** | RVA/偏移绑定当前构建。缓解：类名/klass 回指/值域三重运行时自校验（已内建）+ SHA-256 指纹 + 偏移集中配置；重跑 Il2CppDumper 可再生 |
| ~~静态字段定位失败（spike 风险）~~ | ~~中~~ → **已消除** | 定位链已实测打通（§3.4），方法沉淀在 `mem_probe.py` |
| ACTk 算法变化 | 低 | 已实证本构建算法（§3.3）；换版本重跑反汇编即可 |
| 装备槽/词条运行时结构待摸清 | 中 | P1 内容：定位装备容器与聚合字典（`Dictionary<StatType, ObscuredDouble>` 布局已明确）；词条明细可由 ItemUid 反查云端注册表快照（若走 P0' 存档装配点）或运行时字典 |
| 撕裂读 | 中 | §5.2 校验+重试+择时 |
| 未来版本引入反作弊 | 低 | 每次更新后跑一次 `mem_probe.py` 即可确认读取通道 |
| 触发检测/封号 | 低 | 纯读不触发 ACTk；不做写入/发包能力（设计上就不可能） |
| 账号/条款风险 | 低-中 | 读取**自己账号**的客户端内存做个人数值分析，不触碰服务器协议、不影响他人。缓解：功能默认关闭+手动开启+免责提示；永远不提供写入/发包/注入能力 |
| GC 移动对象 | 低 | IL2CPP 使用 Boehm GC（非移动式），快照期间地址稳定 |

## 7. 限制清单

1. 必须游戏**正在运行且已加载目标角色**（Player/Inventory 单例随角色加载创建）；
2. 只能读到自己进程内的角色，无其他玩家数据；
3. 是客户端快照，非服务器权威实时值（§5.3）；
4. 仅适用当前构建（SHA-256 指纹锁定），更新后需重新导出 schema 并跑探针；
5. Windows 专用（ctypes/WinAPI）；64 位 Python；
6. SO 物品名托管侧不可读，用 ItemUid 反查 `data/so_dump/ItemData.json`。
